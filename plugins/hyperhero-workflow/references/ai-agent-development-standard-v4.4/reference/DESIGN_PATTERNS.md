# AI Agent 設計模式治理與 GoF 23 種模式目錄

> **版本**：4.4.0  
> **載入原則**：本目錄是 Architecture／Domain Profile，不是每次 Builder 任務的必讀全文。只有新增抽象邊界、跨平台實作、工作流／狀態機、複雜物件建立或重大重構時才載入相關模式；一般局部修正優先維持簡單設計。
> **用途**：供 AI Agent 在產碼前評估模式，而非要求每個專案套用所有模式。  
> **最高原則**：先辨識真實問題與變化點，再比較「維持簡單設計」；模式不得取代安全控制。

### 1.3 設計模式治理與 GoF 23 種模式目錄

#### 1.3.1 採用原則與強制約束

本節所列 23 種 Gang of Four（GoF）設計模式，構成本組織的**必要設計模式評估目錄**。每個系統不必實作全部模式，但在需求分析、架構設計、重大重構與 AI 產碼前，必須判斷是否存在適用模式，並留下可驗證的採用或不採用理由。

- **PAT-001 `[CORE]`**：每個新模組、核心用例、跨模組整合與重大重構，必須完成設計模式適用性評估；可得出「不需要設計模式」的結論，但必須說明現有簡單設計已足以滿足哪些需求。
- **PAT-002 `[CORE]`**：設計模式是解決重複設計問題的工具，不是交付目標。禁止為了符合名稱、展示技巧或推測未來需求而建立無實際變化點的介面、抽象層、工廠、事件或繼承樹。
- **PAT-003 `[CORE]`**：應優先採用程式語言、標準函式庫與既有框架已驗證的慣用實作，例如 DI Container Lifetime、Middleware Pipeline、Iterator、Observable、HTTP Client Factory；除非既有能力無法滿足已文件化需求，否則禁止自行重造等價框架。
- **PAT-004 `[CORE]`**：採用或拒絕模式的決策必須記錄於 `/docs/design-patterns.md` 或對應 ADR，至少包含問題、變化點、候選方案、選定模式或不採用、具體參與者、取捨、資安影響、測試與回復方式。
- **PAT-005 `[CORE]`**：若設計模式會影響公開 API、資料模型、交易邊界、非同步語意、安全邊界、部署拓樸、跨模組依賴或組織級慣例，必須建立 ADR 並由對應 Code Owner 審查。
- **PAT-006 `[CORE]`**：模式名稱不得只出現在文件。程式中的角色、責任與依賴方向必須可對映至模式參與者；應使用能表達領域與角色的名稱，避免以 `Manager`、`Helper`、`Util` 掩蓋過度集中的責任。
- **PAT-007 `[CORE]`**：所有模式實作必須明確定義物件生命週期、可變性、Thread Safety、資源釋放、例外傳遞與取消行為。Singleton、Flyweight、Observer、Proxy 與共享 Cache 尤其不得隱含跨請求、跨使用者或跨租戶的可變狀態。
- **PAT-008 `[CORE]`**：設計模式不得取代安全控制。Proxy、Decorator、Facade、Middleware、Mediator、Command Handler 或 UI 隱藏都不能成為唯一授權邊界；權威服務仍必須自行驗證身分、權限、租戶、輸入與業務規則。
- **PAT-009 `[CORE]`**：每個模式實作必須以行為測試證明其價值與限制，至少涵蓋正常流程、替代實作、失敗、逾時、取消、併發及不合法組合；僅具有對應類別名稱或 UML 外觀不構成完成。
- **PAT-010 `[CORE]`**：模式跨越程序或網路邊界時，必須另外處理部分失敗、重試、重複投遞、順序、版本、觀測性與補償；不得把記憶體內 Observer、Command、Proxy 或 Facade 的假設直接套用於分散式系統。
- **PAT-011 `[CORE]`**：AI Coding Agent 在引入新模式前，必須先搜尋 Repository 既有做法，提出候選模式與「維持簡單設計」選項，說明選擇理由、被拒絕方案、參與類別／模組、風險與測試；不得只因 Prompt 出現模式名稱就直接產生樣板程式碼。
- **PAT-012 `[CORE]`**：Code Review 必須主動檢查模式誤用與反模式，包括全域可變 Singleton、Service Locator、God Facade／God Mediator、無限增長的 Factory `switch`、深層繼承、Decorator 順序依賴、事件迴圈、無界責任鏈、未解除 Observer 訂閱與以反射載入不受信任型別。
- **PAT-013 `[CORE]`**：任何依輸入、設定、資料庫或模型輸出選擇具體類別、策略、命令、狀態或解釋器規則的機制，都必須採明確允許清單與伺服器端驗證；禁止把不受信任字串直接用於反射、動態載入、`eval`、腳本或類別名稱解析。
- **PAT-014 `[CORE]`**：`/docs/design-patterns.md` 必須維護目前採用模式、適用模組、Owner、相關 ADR、主要實作位置與已知限制；模式被替換或淘汰時也必須保留遷移與相容性紀錄。
- **PAT-015 `[CORE]`**：更換既有模式或抽象邊界時，必須評估二進位／來源／資料／事件／行為相容性，採分階段遷移並提供 Rollback 或 Roll-forward；禁止在同一 PR 中無需求地全面改寫架構。

#### 1.3.2 建立型模式（Creational Patterns）

| 模式名稱 | 核心說明 | 典型應用場景 | 必要約束與誤用防護 |
|---|---|---|---|
| **單例模式（Singleton）** | 確保一個類別於指定作用域內僅有一個實例，並提供一致的存取方式。 | 資料庫連線池管理器、日誌寫入器、唯讀系統設定快照、Process-level Cache Coordinator。 | 優先由 DI Container 管理生命週期；必須 Thread-safe，預設不可變；不得保存 Request、User、Tenant 或交易狀態；資料庫「連線」本身不得被做成全域 Singleton；禁止演變成 Service Locator 或隱藏依賴。 |
| **工廠方法（Factory Method）** | 定義建立物件的介面或延遲建立步驟，讓具體實作者決定產生哪一種產品。 | 支援信用卡、PayPal、LINE Pay 等支付處理器；依檔案格式建立 Parser／Exporter；依 Provider 建立通知傳送器。 | 可建立的型別必須來自允許清單；不得依不受信任字串任意反射載入；Factory 需驗證設定並回傳明確錯誤；若 `switch` 持續增長，應評估 Registry、DI 或 Abstract Factory。 |
| **抽象工廠（Abstract Factory）** | 提供建立一整套相關或相依物件的介面，而不暴露具體類別。 | 建立 macOS／Windows UI 元件家族；不同雲端供應商的一組 Storage、Queue、Secret 與 Identity Adapter；不同資料庫方言的一組元件。 | 同一產品家族必須保持相容，禁止混搭造成隱性錯誤；每個家族須有 Contract Test；不得僅為包裝單一產品建立多層工廠；新增產品種類時須評估所有工廠的相容性成本。 |
| **建造者模式（Builder）** | 將複雜物件的分步構建與最終表示分離，使相同構建流程可產生不同表示。 | 構建複雜 HTTP Request、不可變設定物件、測試資料、文件、參數化 SQL AST／Query Object。 | `Build()` 前必須驗證必要欄位與不變條件；完成物件應優先不可變；不得以字串串接產生 SQL、Shell 或 HTML；Secret 不得出現在 `ToString()`、Log 或 Snapshot；避免同時存在大量無效中間狀態。 |
| **原型模式（Prototype）** | 透過複製既有實例建立新物件，避免重複昂貴的初始化或組態流程。 | 複製成本高的模板、預先解析的唯讀設定、複雜圖形／文件節點、測試資料原型。 | 必須明確定義 Deep Copy／Shallow Copy；新物件的 ID、Owner、Audit 欄位與生命週期不得錯誤沿用；禁止複製 Token、Secret、Socket、DB Context、Lock 或未完成交易；可變集合與跨租戶資料不得共享參照。 |

#### 1.3.3 結構型模式（Structural Patterns）

| 模式名稱 | 核心說明 | 典型應用場景 | 必要約束與誤用防護 |
|---|---|---|---|
| **適配器模式（Adapter）** | 將既有介面轉換為客戶端期望的介面，使不相容元件可合作。 | 串接舊系統 API；把第三方金流、物流、身分或 AI SDK 整合至內部 Port；資料格式轉換。 | Adapter 應位於外部邊界，避免第三方型別滲入 Domain；必須轉譯錯誤、Timeout、取消、Rate Limit 與資料分類；需有 Contract Test；不得在轉換過程繞過驗證或遺失租戶／授權 Context。 |
| **橋接模式（Bridge）** | 將抽象與實作分離，使兩個變化維度可以獨立演化。 | 形狀與繪圖 API 分離；通知內容與傳送通道分離；儲存抽象與雲端／本地實作分離。 | 必須確有兩個可獨立變化的維度；若只有單一實作，優先使用簡單組合；抽象與實作契約需各自版本化並有組合測試；不得讓 Bridge 隱藏不相容的安全或一致性語意。 |
| **組合模式（Composite）** | 將物件組合成樹狀結構表示部分－整體，使葉節點與組合節點可用一致介面處理。 | 檔案與資料夾、UI 元件樹、組織／權限樹、規則或工作流程節點。 | 必須防止循環、過深遞迴與超大樹造成 DoS；每個節點仍要做物件層授權；批次操作需定義部分失敗與交易語意；禁止因一致介面而忽略葉節點與容器的不同限制。 |
| **裝飾模式（Decorator）** | 在不改變原物件介面的情況下，動態疊加額外責任。 | Middleware、請求追蹤、重試／快取／量測包裝、Java I/O Stream、Feature Policy。 | Decorator 順序必須明確、可測試且可觀測；不得重複執行具副作用操作；授權、交易與輸入驗證不可因包裝順序被繞過；避免形成難以追蹤的過深鏈；取消與 Exception Cause 必須完整傳遞。 |
| **外觀模式（Facade）** | 為複雜子系統提供高階且一致的入口，降低呼叫端對內部細節的耦合。 | 一鍵下單協調庫存、訂單、付款與物流；應用服務入口；對多個 SDK 提供統一 API；API Gateway 的部分整合職責。 | Facade 不得成為 God Object；不得假設跨服務呼叫具單一 ACID 交易；權威子系統仍須自行授權與驗證；需定義補償、部分失敗與可觀測性；不得把所有 Domain 邏輯集中於單一入口。 |
| **享元模式（Flyweight）** | 將大量細粒度物件的內在共享狀態抽出並重用，以降低記憶體與建立成本。 | 文字編輯器共享字型／樣式、遊戲大量粒子或樹木、唯讀規則元資料、符號表。 | 共享的 Intrinsic State 必須不可變且不得包含 User、Tenant、權限或 Secret；外在狀態由呼叫端明確提供；需監控 Cache／Pool 上限與清除策略；不可為節省少量記憶體而增加同步與資料外洩風險。 |
| **代理模式（Proxy）** | 以代理物件控制、延遲或擴充對目標物件的存取。 | Lazy Loading、Protection Proxy、Caching Proxy、Remote Proxy、Rate-limited Client。 | 目標服務仍必須自行驗證授權；Cache Key 必須包含 Tenant、Principal 與影響結果的 Context；不得隱藏遠端呼叫成本與失敗；需傳遞 Timeout／取消／Trace；禁止以 Proxy 作為唯一安全邊界或靜默改變交易語意。 |

#### 1.3.4 行為型模式（Behavioral Patterns）

| 模式名稱 | 核心說明 | 典型應用場景 | 必要約束與誤用防護 |
|---|---|---|---|
| **責任鏈模式（Chain of Responsibility）** | 將請求依序傳遞給多個處理器，使發送者不必綁定單一接收者。 | HTTP Filter／Middleware、驗證與授權管線、請假審核流程、內容檢查管線。 | 處理順序、短路條件、終止處理器與預設拒絕必須明確；禁止因漏掛 Handler 造成安全繞過；需限制鏈長與循環；具副作用 Handler 必須具冪等或補償；每步要可追蹤。 |
| **命令模式（Command）** | 將請求封裝成可傳遞、排程、記錄或復原的物件。 | Undo／Redo、工作佇列、CQRS Command、批次任務、遙控器按鍵映射。 | Command Payload 必須版本化、最小化且優先不可變；執行時重新授權，不得只在入列時檢查；需定義冪等鍵、重試、逾時、取消與重播；不是所有動作都可 Undo，補償不得被誤稱為原子回復。 |
| **解釋器模式（Interpreter）** | 定義有限語言的文法與解釋流程，以處理規則或表達式。 | 自訂規則引擎、查詢 DSL、數學算式、篩選條件、政策表達式。 | 必須採正式 Grammar／AST 與允許清單；禁止把輸入交給 `eval`、Shell 或任意程式碼引擎；需限制深度、步數、時間、記憶體與函式能力；錯誤位置要可診斷；安全關鍵政策需版本化與審查。 |
| **迭代器模式（Iterator）** | 提供循序存取聚合內容的方法，而不暴露其內部表示。 | 集合巡覽、資料庫 Cursor、分頁 API、串流處理、檔案逐筆讀取。 | 大資料集必須採 Lazy／Paging／Streaming 與上限；明確定義並行修改語意；Cursor、Stream、DB Reader 必須可釋放；避免重複枚舉觸發多次 I/O；不得以 Iterator 掩蓋無界查詢。 |
| **中介者模式（Mediator）** | 由中介物件封裝多個元件之間的互動，降低直接相互引用。 | 聊天室伺服器、UI Dialog 協調、應用內 Command／Notification Mediator、飛航管制類協調。 | 禁止演變為 God Mediator 或 Service Locator；訊息與責任需明確、可追蹤；核心 Domain 不應只剩轉送器；跨程序時必須處理交付與失敗語意；不得讓 Mediator 成為未驗證的權限繞道。 |
| **備忘錄模式（Memento）** | 在不破壞封裝的前提下保存物件狀態，以便日後還原。 | 遊戲存檔、文字草稿、表單復原、設定版本、編輯器 Undo Snapshot。 | Snapshot 必須分類、加密、版本化、具 TTL 與存取控制；不得包含不必要 Secret、Token 或跨租戶資料；還原前必須重新驗證 Schema、Owner 與授權；需控制儲存量並處理新版程式讀取舊狀態。 |
| **觀察者模式（Observer）** | 建立一對多依賴，當主體狀態改變時通知所有訂閱者。 | UI Reactive State、Domain Event Listener、Pub/Sub、RxJS、監控通知。 | 必須管理訂閱與解除訂閱，避免 Memory Leak；定義同步／非同步、順序、重試與失敗隔離；分散式事件需版本化、冪等、Backpressure 與 Dead Letter；不得假設通知必定一次且即時送達。 |
| **狀態模式（State）** | 將狀態特有行為封裝，使物件在狀態轉換時改變可執行行為。 | 訂單、申請、票證、付款、工作流程狀態機；連線生命週期。 | 必須有明確狀態轉移表與禁止轉移；轉移由 Server 原子驗證並處理併發；每次轉移需稽核 Actor、原因與時間；禁止只靠前端按鈕限制；需定義終止、失敗、取消與補償狀態。 |
| **策略模式（Strategy）** | 將一系列可替換演算法封裝在共同契約下，使呼叫端不依賴具體演算法。 | 折扣、稅額、路線規劃、排序、風險評分、模型／Provider 選擇。 | Strategy 必須由允許清單或受控設定選擇；每個策略需有相同契約與測試；需定義找不到策略、失敗與 Fallback；涉及權益或 AI 決策時，要記錄實際策略與版本；禁止載入不受信任程式碼。 |
| **範本方法模式（Template Method）** | 在基底類別定義演算法骨架，將部分步驟延後由子類別實作。 | Framework Lifecycle Hook、匯入／匯出流程、固定步驟的批次處理。 | 基底流程與可覆寫 Hook 必須清楚且穩定；子類不得破壞不變條件與安全檢查；避免深層繼承與 Fragile Base Class；當變化維度多或需執行期替換時，優先考慮 Strategy／Composition。 |
| **訪問者模式（Visitor）** | 將作用於資料結構元素的操作外移，使新增操作時不必修改各元素類別。 | 編譯器 AST 分析、文件／報表匯出、規則樹檢查、序列化與靜態分析。 | 新增元素類型時必須讓未處理 Visitor 可被編譯器或測試偵測；需控制遞迴深度與惡意 AST；Visitor 不得取得超出需求的內部敏感資料；若元素類型頻繁變動，須重新評估其維護成本。 |

#### 1.3.5 模式選型與驗證流程

設計者與 AI 必須依下列順序執行，不得先選模式再尋找問題：

1. **描述問題與變化點**：指出目前重複、耦合、建立、組合或互動困難，以及實際會變動的維度。
2. **確認非功能約束**：列出安全、租戶、資料、交易、效能、併發、生命週期、可觀測性與相容性要求。
3. **盤點既有方案**：搜尋現有模組、框架與標準函式庫；優先沿用既有慣例。
4. **比較候選**：至少比較「維持簡單設計」與一個候選模式；重大變更應比較兩個以上候選。
5. **具體角色對映**：將模式中的 Creator、Product、Subject、Observer、Command、State、Strategy 等角色對映到實際類別、函式、模組或服務。
6. **威脅與失敗分析**：檢查不受信任選擇、權限繞過、跨租戶狀態、重複副作用、資源耗盡、事件循環與序列化風險。
7. **以測試證明**：測試替換性、組合性、失敗、併發與模式特有風險，而不是只測 Happy Path。
8. **記錄與演進**：更新 Pattern Decision Record、ADR、架構圖、Owner、限制、Migration 與回復方式。

> **判定原則**：模式目錄與評估流程是強制的；具體模式的實作屬「適用時必須」。在沒有真實變化點或複雜度時，簡單函式、模組、組合與明確資料結構通常優於模式化樣板。
